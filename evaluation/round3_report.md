### 원인 분석 (검색 / 프롬프트 / 도구 / 가드)

**응답 시간 (라운드 2의 e11, 63.75초)**
- 서버 처리 63,749ms 중 도구는 4ms였다. 시간은 모델 호출에서 쓰였다.
- 확인한 사실: 모델 클라이언트의 기본 설정이 읽기 제한 60초, 연결 제한 60초, 재시도 기본 방식(최대 5회)이었다.
  첫 시도가 응답 없이 60초 제한까지 걸려 끊긴 뒤 재시도가 3.7초에 성공했다면 60 + 3.7 ≈ 63.7로 숫자가 맞는다. 다만 그 순간에 실제로 무슨 일이 있었는지는 기록으로 확인하지 못했다. 이 부분은 추정이다.
- 분류: 모델 호출 설정 문제 (검색, 프롬프트, 도구, 가드와 무관).

**검증 — 무엇을 확인했고 무엇은 못 했는가**
- 확인함: 응답 없이 연결만 받는 가짜 서버로 멈춘 모델 호출을 재현했다. 제한 1초 × 2회 시도에서 호출이 2~3초 안에 끊기고, 예비 모델로 넘어가며,
  다음 호출은 쿨다운 때문에 기다리지 않는다(0.5초 미만). 기본 설정(60초)이었다면 같은 상황에서 1분 넘게 기다린다.
- 확인함: 실제 모델 40문항에서 정상 호출은 새 제한(15초)에 걸리지 않았다. 최대 7.27초, 평균 2.68초, 단순 조회 평균 2.68초이고 40문항 모두 Sonnet 4.6이 답했다(예비 모델로 밀린 문항 없음).
- **못 한 것**: 라운드 3에서는 라운드 2의 63초 같은 멈춤이 다시 일어나지 않았다. 그래서 "실제 서비스에서 같은 멈춤이 와도 짧아진다"는 것은 가짜 서버 시험으로만 확인했다.
  멈춤이 드물어서 실제로 다시 만나기 전에는 실측으로 확인할 수 없다.
- 트레이드오프: 읽기 제한 15초는 정상 응답의 최대(약 8초)보다 넉넉하지만, 아주 긴 정상 응답이 15초를 넘기면 불필요하게 끊긴다. 이번 측정에서는 그런 경우가 없었다.
  멈춤이 한 번 일어나면 최악의 경우 앞 모델에서 약 30초(15초 × 2회)를 쓴 뒤 예비 모델로 넘어간다. 이전의 60초 이상보다는 짧지만 여전히 길다.

**나머지 점수 (규칙 40/40, 라운드 2와 같다)**
- 라운드 2와 3은 답변 로직이 같다. 두 라운드 사이에서 규칙 판정 결과, 도구 호출, 검색된 근거는 40문항 모두 같았다.

  RAGAS 평균은 faithfulness 0.931 → 0.931, context precision 0.944 → 0.958, context recall 1.0 → 1.0이다.
- 흔들림 폭에 대한 해석: 라운드 1, 2, 3의 RAGAS faithfulness 평균은 0.833, 0.931, 0.931이다. 라운드 2와 3은 거의 같았지만, 라운드 1과 2는 정책 질문을 안 건드렸는데도 0.1 차이가 났다.
  표본이 3번뿐이라 흔들림 폭을 한 숫자로 말할 수는 없고, "0.1 안팎은 시스템을 고치지 않아도 움직일 수 있다"까지만 말할 수 있다.
