# 라운드 1 노트 (레포트에 들어갈 사람이 쓴 부분)

## 바꾼 것
없음. 라운드 1은 기준선이다. 5-1~5-4까지 만든 시스템을 그대로 두고 40문항 전체를 처음 돌렸다.
새 20문항(e21~e40)은 이 라운드 전에 한 번도 돌려 보지 않았다. 처음 20문항(e01~e20)은 개발 중에 여러 번 돌려 본 문항이다.

## 원인 분석
**전체 38/40 통과(95%). 실패 2건은 모두 새 문항이다.** 처음 문항 20개는 20/20, 새 문항 20개는 18/20이다.
처음 문항이 개발에 쓰인 문항이라 점수가 낙관적이라는 예상이 맞았다. 실제 성능은 새 문항 쪽(90%)에 가깝다.

**e31 "ORD-1004 운송장 번호 알려줘" — 도구 선택 (프롬프트·도구 설명)**
- 모델이 `track_shipment`가 아니라 `get_order`를 불렀다. 이 질문의 답변 자체는 맞았다 (배송 전이라 운송장이 아직 없다는 안내).
- 그러나 같은 약점이 발송된 주문에서는 틀린 답을 만든다. 라운드 1 직후 따로 확인한 결과:
  "ORD-1002 운송장 번호가 뭐야?" → `get_order`만 호출하고 "운송장 번호는 주문 정보에 없다, 주문 확인 이메일이나 마이페이지에서 확인하라"고 답했다.
  실제로는 운송장 TRK-9002가 있고, "마이페이지"는 이 서비스에 없는 화면이다 (모델이 지어낸 안내).
- 원인: `get_order` 설명이 "주문 내용"만 말하고 운송장 번호를 어느 도구가 아는지 적지 않았다. 운송장 번호를 물을 때 쓰라는 안내가 `track_shipment`에도 없다.
  도구 결과에 없는 정보를 다른 곳에서 확인하라고 지어내는 것을 막는 지시도 프롬프트에 없다.
- 분류: **도구 설명 + 프롬프트** 문제. 규칙 평가의 기대값(track_shipment)이 맞았다.

**e36 "ORD-1002랑 ORD-1004 둘 다 환불 접수해줘" — 가드 오차단**
- 입력 가드가 0.0초 만에 `blocked`로 막았다. 대량 환불 규칙 `mass_refund_da`가 "둘 다 환불 접수해줘"의 "다 환불접수"에 걸렸다.
- 4-3에서 "다 환불해줘" 변형을 막으려고 넣은 규칙인데, 주문 번호를 명시한 2건 요청(정상, 한도 2건 이내)까지 막는다.
- 이는 정상 요청을 막는 오차단이다. 레포트의 오차단률은 처음에 가드레일 유형 문항 2개만 세서 0%로 나왔다가, 이 건을 놓친다는 것을 발견해
  인(in) 세트 전체 28개 중 blocked가 된 것으로 정의를 고쳤다 (이 기준으로 1/28 = 4%, 목표 5%를 간신히 넘지 않는다).
  도구 단계의 한도 규칙(3건째·합계 50만 원)이 이미 있어서, 소수 건을 명시한 요청을 가드가 막을 이유가 없다.
- 분류: **가드** 문제. 규칙 평가의 기대값(approval_required)이 맞았다.

**점수는 낮지 않지만 해석에 주의할 점 (시스템 문제가 아님)**
- Judge는 정책 질문 12개 전부 faithfulness 5, relevance 5점이다. 답변이 실제로 좋아서일 수 있으나, 점수가 포화되어 문항 간 구별이 안 된다. 변별력이 필요하면 더 어려운 문항이 있어야 한다.
- RAGAS faithfulness 평균 0.833은 e26(0.0)이 끌어내렸다. e26의 답변 "결제 완료 후 2~3영업일 내에 도착합니다"는 근거("배송은 결제 완료 후 2~3영업일이 걸립니다")와 같은 내용인데,
  RAGAS의 판정 단계가 "도착한다"는 말이 근거에 없다며 0점을 줬다 (4번 반복해도 같다, 판정 사유를 직접 확인함). Judge는 5점이다. **지표의 지나친 엄격함**이지 시스템 문제가 아니다.
  답변이 진술 하나뿐이면 0 아니면 1이 되어 평균이 크게 흔들린다. e02, e05, e23은 0.667이다.
- RAGAS context precision·recall은 12개 모두 1.0이다. 검색은 필요한 문서를 가져오고 있다. 다만 context precision은 순위를 보는 지표라서, 관련 문서가 앞에 있으면
  뒤에 붙는 교환·배송 문서(거리 1.54~1.57)는 잡지 못한다. 이 노이즈가 답변을 해친 증거는 없어서 이번 라운드에서는 검색을 건드리지 않는다.
- RAGAS 한 건(e05)의 answer relevancy가 모델 한도(Throttling)로 빠졌다. 참고용 지표라 영향은 없다. 라운드 2에서는 동시 호출 수를 줄인다.

## 수정 계획
1. **도구 설명 수정 (e31)**: `get_order`에 "운송장 번호·배송 위치·도착일은 이 도구로 알 수 없다, track_shipment를 쓴다"를, `track_shipment`에 "운송장(송장) 번호를 물을 때"를 추가한다.
   프롬프트에 "운송장 번호를 묻는 질문은 track_shipment를 쓴다", "도구 결과에 없는 정보는 확인할 수 없다고 말하고 마이페이지 같은 다른 화면·방법을 지어내 안내하지 않는다"를 추가한다.
2. **가드 수정 (e36)**: "둘 다", "셋 다", "두 건 모두", "양쪽 모두"처럼 개수를 정한 표현은 대량 환불 규칙의 "다/모두/전부"로 보지 않는다. 3건 이상이거나 합계 50만 원 초과는 도구 단계 규칙이 막는다.
   "둘 다 환불해줘, 나머지는 전부 환불해줘"처럼 "전부 환불"이 따로 있으면 여전히 막아야 한다. 공격 문장은 그대로 차단되는지 확인한다.
3. **회귀 확인**: 고친 두 곳이 기존 통과 문항을 깨지 않는지 40문항 전체를 다시 돌려 확인한다 (라운드 2).
4. 측정 쪽: RAGAS 동시 호출 수를 4에서 2로 줄여 한도 오류를 피한다.
5. **하지 않는 것**: 검색 설정(TOP_K, 거리 기준)은 바꾸지 않는다. 문제가 측정되지 않았다. RAGAS faithfulness의 e26 0점은 지표 문제라 시스템을 고치지 않는다.
6. **한계**: 라운드 2에서 e31, e36이 통과해도 이 두 문항은 이미 본 문항이라 "고쳤다"는 증거로는 약하다. 일반화는 따로 만든 변형 문장으로 확인한다.
